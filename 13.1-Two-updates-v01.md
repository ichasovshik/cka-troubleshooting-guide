# Why `subPath: app.conf` is correct for `/etc/current.conf`

First, create the ConfigMap that provides the source files:

```bash
kubectl -n ks-q10-5 create configmap app-files \
  --from-literal=app.conf=mode=practice \
  --from-literal=logging.conf=level=info
```

## Mount example

```yaml
volumeMounts:
- name: cfg-files
  mountPath: /etc/current.conf
  subPath: app.conf
  readOnly: true
```

```yaml
volumes:
- name: cfg-files
  configMap:
    name: app-files
```

## How this works

- ConfigMap `app-files` has keys: `app.conf` and `logging.conf`.
- A ConfigMap volume exposes each key as a file with the same name.
- `subPath: app.conf` selects that one source file from the volume.
- `mountPath: /etc/current.conf` is the target path in the container.

So the container reads `mode=practice` from `/etc/current.conf`.

## Common mistake

Using `subPath: current.conf` is incorrect unless the volume actually contains a file named `current.conf`.

## Rule of thumb

- `subPath` = source filename/key from the volume.
- `mountPath` = destination path inside the container.

# Optional Secret and ConfigMap References: Why `optional: true` Did Not Help

## The incident

In Q.10-5, the Pod stayed in `ContainerCreating`.

Its events showed:

```text
MountVolume.SetUp failed for volume "creds":
secret "app-secret" not found
```

The Pod referenced `app-secret` in two independent ways:

1. An environment variable: `DB_USER`, sourced from key `db-user`.
2. A volume: `creds`, exposing the Secret as files.

Adding `optional: true` to the environment-variable reference did not
make the volume reference optional.

## 1. What an optional key reference actually does

Example fragment from a container:

```yaml
env:
- name: DB_USER
  valueFrom:
    secretKeyRef:
      name: app-secret
      key: db-user
      optional: true
```

This tells Kubernetes:

> Do not block this container's environment setup if this Secret or
> this key is missing.

For this reference:

| Situation | Result |
|---|---|
| Secret and key exist | Populate `DB_USER` with the key's value |
| Secret is missing | Skip this environment-variable entry |
| Secret exists but key is missing | Skip this environment-variable entry |

Skipping the entry does **not** mean Kubernetes sets `DB_USER` to an
empty string or generates a default value.

In this lab, with no other source defining it, `DB_USER` would be unset.

The equivalent ConfigMap key-reference field is:

```yaml
env:
- name: RUN_MODE
  valueFrom:
    configMapKeyRef:
      name: app-env
      key: APP_MODE
      optional: true
```

## 2. Optionality is local to each reference

Our Pod also contained this required volume reference:

```yaml
volumes:
- name: creds
  secret:
    secretName: app-secret
```

There is no `optional: true` here.

Therefore, even though the environment-variable reference was optional,
the Secret volume remained required.

Think of the references separately:

```text
app-secret
├── DB_USER environment reference → optional
└── creds volume reference        → required → blocks startup if missing
```

Changing one branch does not change the other.

Common locations for optional references:

| Purpose | Field |
|---|---|
| One Secret key as an environment variable | `env[].valueFrom.secretKeyRef.optional` |
| One ConfigMap key as an environment variable | `env[].valueFrom.configMapKeyRef.optional` |
| All environment variables from a Secret | `envFrom[].secretRef.optional` |
| All environment variables from a ConfigMap | `envFrom[].configMapRef.optional` |
| Secret-backed volume | `volumes[].secret.optional` |
| ConfigMap-backed volume | `volumes[].configMap.optional` |

These are independent settings—not a Pod-wide switch.

## 3. Optional to Kubernetes does not mean optional to the application

Our writer command began with:

```sh
set -eu
echo "DB_USER=$DB_USER"
```

The `-u` shell option treats expansion of an unset variable as an error.

Even if Kubernetes allows startup without the optional Secret key,
the shell can still exit when it expands an unset `DB_USER`.

There are two distinct failure stages:

| Stage | Example |
|---|---|
| Before the container starts | A required Secret volume cannot be mounted |
| After the container starts | The application or shell fails because a value is absent |

Use optional references only when the application can actually tolerate
the missing configuration.

For required credentials, keep the dependency required and provide it.

## 4. What actually fixed our missing-Secret problem

The namespace contained `app-env-secret`, but not `app-secret`.

These were different resources with different purposes:

| Secret | Keys | Purpose |
|---|---|---|
| `app-env-secret` | `API_TOKEN` | Reader's `envFrom` |
| `app-secret` | `db-user`, `db-password` | Writer's environment and credential files |

Check the resources:

```bash
kubectl -n ks-q10-5 get secrets
kubectl get secrets -A --field-selector metadata.name=app-secret
```

Secrets in other namespaces do not satisfy this Pod's references.

Create the missing Secret using dummy lab values:

```bash
kubectl -n ks-q10-5 create secret generic app-secret \
  --from-literal=db-user=labuser \
  --from-literal=db-password=dummy-pass-105
```

Kubelet retries required Secret volume setup. Creating the missing Secret
can resolve the mount failure without deleting the Pod.

For this exercise, `DB_USER` is required, so remove the temporary
`optional: true` workaround, or set it to `false`.

## 5. Separate blockers require separate fixes

Creating `app-secret` resolved the missing-volume dependency.

It did not resolve the next error:

```text
sh: can't create /data/read.log: Read-only file system
```

That was a different problem: reader attempted to write through a
read-only mount.

Likewise, optional references do not fix:
- Read-only mount permissions.
- Missing application-level defaults.
- Container startup races.
- Local manifest edits that have not been applied.

## Exam memory rule

**Optional reference ≠ optional resource everywhere ≠ application default.**

Debug in order:

1. Read Pod events.
2. Identify the exact missing resource and namespace.
3. Check every reference to that resource.
4. Fix the required dependency.
5. Once containers start, inspect their logs for runtime failures.
